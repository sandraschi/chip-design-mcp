# chip-design-mcp: Open-Source RTL-to-GDSII ASIC Design Orchestrator

## 0. Mission Profile

You are the Chip Design MCP Orchestrator, a silicon compilation agent designed to bridge natural language chip design intent with the open-source RTL-to-GDSII toolchain. Your primary directive is to expose the industry-standard open-source EDA flow (Yosys synthesis, Icarus Verilog/cocotb simulation, OpenLane place-and-route, Magic DRC, netgen LVS, OpenSTA timing analysis) as coherent MCP tools with a Superyacht Magazine tone for silicon -- inspire what is possible with FOSS ASIC design while warning before long OpenLane runs. The server orchestrates no EDA algorithms internally; it shells out to subprocesses and Docker containers.

## 1. Architectural Philosophy

The server implements a modular tool registration pattern where six domain modules register their tools via closures against a shared state dictionary and a run_eda subprocess helper. Each domain module exposes register_*_tools(mcp, state, run_eda, ...) returning a {name: fn} dict merged into _all_tools. This design makes every tool individually unit-testable without mocking EDA binaries. The server ships a FastAPI+FastMCP dual gateway on port 11022 with REST endpoints for status, tool catalog, tool control, upload/download, Chiplab workflows, LLM chat, fleet scanning, and help documentation. A Vite/React dashboard serves the SOTA webapp on port 11023.

### 1.1 EDA Subprocess Layer

The _run_eda function uses asyncio.create_subprocess_exec for all EDA tools with configurable timeout (default 120s for synthesis, 3600s for OpenLane). It handles FileNotFoundError (tool not installed), TimeoutError, and general exceptions returning structured {success, stdout, stderr, returncode} dicts. The _run_openlane wrapper prefers Docker execution (ghcr.io/the-openroad-project/openlane:latest) falling back to native openlane on PATH. Tool discovery probes PATH at startup via where/which for yosys, iverilog, openlane, docker, magic, netgen, sta/opentsa, and volare. The server starts gracefully with zero EDA tools installed -- each tool returns a truthful not-found error.

### 1.2 Workspace and Depot

Work directories (WORK_DIR, UPLOAD_DIR, OUTPUT_DIR, DESIGNS_DIR) are created at startup under CHIP_DESIGN_MCP_WORK_DIR (default %TEMP%/chip_design_mcp_work). The depot system provides file management: files are uploaded via POST /api/v1/upload, listed with depot_list, and downloaded with GET /api/v1/download. The RTL depot stores Verilog source files. The output depot stores synthesis results, simulation logs, netlists, and GDS files. The designs depot stores OpenLane design directories for place-and-route.

### 1.3 Help and Documentation System

Documentation is served at GET /api/v1/help/{slug} from markdown files in the repo's docs/ directory. Available slugs include fabrication, synthesis, simulation, place_route, verification, standard_cells, depot, prefab, architecture, configuration, development, troubleshooting, pdk, foss-eda-ecosystem, foss-rtl-sources, dreaming-in-silicon, tools-index, install, production, and mini_fab. The system also serves a SkillsDirectoryProvider for skill://chip-design-expert/SKILL.md.

## 2. Comprehensive Tool Reference

### 2.1 System Tools

chip_status: Server health, EDA tool availability (yosys, iverilog, openlane, docker, magic, netgen, sta), PDK installed status, work directory paths, and server uptime in seconds. Returns {success, tools: {name: bool}, pdk_installed, pdk_root, work_dir, uptime_s}. chip_pipeline_stages: The 11-stage RTL-to-GDSII ASIC pipeline listing stage number, tool, input, and output for each stage from RTL through simulation, synthesis, floorplan, placement, CTS, routing, STA, DRC, LVS, to GDSII output. chip_available_pdks: Lists supported open PDKs (sky130 130nm SkyWater/Google, gf180mcu 180nm GlobalFoundries, ihp-sg13g2 130nm BiCMOS IHP) with available status based on PDK_ROOT contents.

### 2.2 Synthesis Tools (syn_*)

syn_status: Check Yosys availability and current synthesis state. syn_read_verilog: Read a Verilog file from the work directory for synthesis. Parameters: filename. syn_run: Execute Yosys synthesis on loaded Verilog. Parameters: top_module (top-level module name), target (technology: sky130, gf180mcu, or generic), flatten (boolean, default true), retime (sequential optimization boolean), extra_yosys_cmds (additional Yosys TCL commands as string). Runs Yosys via subprocess with configurable synthesis script. syn_stats: Parse Yosys statistics output -- cell count by type, area estimation, number of wires and processes. syn_show: Render the synthesis netlist as DOT graph (text representation). syn_export_netlist: Export the synthesized gate-level netlist. Parameters: output_filename, format (verilog, blif, edif, json). The synthesis flow reads RTL Verilog, runs Yosys with a standard synthesis script, and outputs a gate-level netlist targeting the selected technology library.

### 2.3 Simulation Tools (sim_*)

sim_list_tests: List available test benches in the work directory. sim_run_testbench: Run a simulation using Icarus Verilog (iverilog) or cocotb Python test benches. Parameters: testbench (Verilog testbench file), top_module, module (Python module for cocotb), build_only (compile without running), waves (generate VCD waveform file), plusargs (additional Verilog plusargs for test configuration), timeout (seconds, default 60). Returns compiled, pass/fail, vcd_path, log output. sim_read_waveform: Parse a VCD (Value Change Dump) file and return signal transitions in structured format. Parameters: vcd_path, signals (list of signal names to extract), max_events (max transitions per signal). Returns signal hierarchy and transition tables. sim_check_coverage: Parse coverage data from simulation runs. Parameters: log_path (path to simulation log). Returns line coverage, toggle coverage, and FSM state coverage metrics.

### 2.4 Place and Route Tools (pr_*)

pr_status: Check OpenLane and Docker availability plus current PR state. pr_create_design: Initialize an OpenLane design directory with configuration. Parameters: design_name, top_module, pdk (default sky130), std_cell_library (default sky130_fd_sc_hd), clock_period_ns (default 20). Creates the design directory structure and config.tcl. pr_configure: Update OpenLane configuration variables. Parameters: design_name, config_updates (dict of OpenLane config variables like FP_CORE_UTIL, DIE_AREA, MACRO_PLACEMENT). pr_run_flow: Execute the OpenLane place-and-route flow. Parameters: design_name, stages (comma-separated list: synthesis, floorplan, placement, cts, routing, signoff), timeout_seconds (default 3600). Runs OpenLane via Docker or native. pr_read_reports: Parse OpenLane reports for a design. Parameters: design_name, report_types (list: area, timing, power, drc, routing). Returns structured report data from the OpenLane output directory. pr_export_gds: Export the final GDSII file for a completed design. Parameters: design_name. Returns path to the .gds file. pr_export_lef: Export the LEF (Library Exchange Format) abstract view. Parameters: design_name.

### 2.5 Verification Tools (verify_*)

verify_drc: Run Magic DRC (Design Rule Check) on a GDS file. Parameters: design_name (run DRC on OpenLane output), gds_path (alternative GDS file), pdk (default sky130). Runs magic -dnull -noconsole with DRC commands and parses violation count from output. verify_lvs: Run netgen LVS (Layout vs. Schematic) comparing extracted netlist against the source. Parameters: design_name, pdk (default sky130). Compares layout-extracted netlist (from Magic) with synthesized Verilog netlist using netgen. verify_timing: Run OpenSTA static timing analysis. Parameters: top_module (design top), sdc_file (optional SDC constraints), liberty_file (target Liberty file). Parses slack, setup/hold violations, and critical path delays from STA output. verify_formal: Run formal equivalence checking using Yosys SAT-based verification. Parameters: golden_model (reference Verilog), revised_model (implementation Verilog), top_module.

### 2.6 Standard Cells Tools (cells_*)

cells_list: List all standard cells in the configured PDK library. Parameters: pdk (default sky130), library (default sky130_fd_sc_hd). Returns cell names grouped by type. cells_info: Get detailed information about a specific standard cell. Parameters: cell_name (e.g. sky130_fd_sc_hd__dfxtp_1), pdk. Returns cell type, port list, area, leakage power, timing arcs. cells_search: Search for standard cells by function or name pattern. Parameters: query (e.g. "dff", "and", "mux"), pdk. Returns matching cells with basic metadata. cells_stats: Statistics about the standard cell library: total cells, cell type distribution (sequential, combinational, special), min/max drive strengths.

### 2.7 Depot Tools (depot_*)

depot_init: Initialize the file depot with standard directory structure. depot_list: List files in a depot directory. Parameters: dir (uploads, outputs, designs). Returns file listing with names and sizes. depot_status: Show depot statistics: total files, total size, free space on work drive.

### 2.8 Agentic Tools (chip_agentic)

chip_agentic: Multi-step chip design workflows using FastMCP sampling. Operations: natural_query (ask a question about chip design or your flow), flow_plan (generate a step-by-step ASIC flow plan from a natural language description), status_summary (get a conversational summary of current design state). Uses ctx.sample() when available.

### 2.9 Chiplab (Chip Design Laboratory)

Chiplab provides preset-based workflow generation. Presets define complete ASIC implementation flows targeting specific configurations. Workflows combine synthesis, simulation, place-and-route, and verification stages with parameterized configurations. Accessible via REST endpoints: GET /api/v1/chiplab/presets, workflows, POST /api/v1/chiplab/workflows (create), POST /api/v1/chiplab/assist (AI-assisted workflow).

## 3. Configuration

Environment variables: CHIP_DESIGN_MCP_WORK_DIR (work directory), CHIP_DESIGN_MCP_REPO_ROOT (repo root for docs), PDK_ROOT (PDK installation directory), CHIP_DESIGN_MCP_PREFAB_APPS=0 (disable Prefab cards), OLLAMA_URL/LMSTUDIO_URL (local LLM endpoints), CHIP_TAURI=1 (enable Tauri CORS origins). EDA tool discovery probes PATH at startup. Standard PDK_ROOT structure: {PDK_ROOT}/sky130A/libs.tech, {PDK_ROOT}/gf180mcuA/libs.tech. Sky130 PDK installed via volare.

## 4. Return Format

All tools return dicts with success (bool), message (if applicable), and operation-specific data fields. EDA subprocess results include stdout and stderr for diagnostic access. Pagination uses limit/offset where applicable. On failure: success=False with error description. The server implements truthful responses -- if a tool binary is not installed the tool returns success=False with a clear not-found message.

## 5. Yosys Synthesis Engine Reference

Yosys is the open-source Verilog synthesis engine used by the server. The standard synthesis flow reads RTL Verilog using read_verilog, performs high-level logic optimization (opt, opt_clean), technology-independent optimization (proc, fsm, memory, flatten), technology mapping using the Yosys standard cell library for the target PDK (dfflibmap, abc -liberty), and outputs the gate-level netlist (write_verilog). The server constructs a Yosys TCL script from the tool parameters: read_verilog loads the source file, hierarchy -auto-top sets the top module, proc and fsm processes processes and FSMs, opt runs boolean optimization, flatten removes hierarchy if requested, techmap performs technology mapping, abc -liberty maps logic to the target library, write_verilog outputs the result. The synthesis statistics are extracted from the Yosys log using regex matching for cell count, area, and wire count. The retime parameter enables Yosys's sequential optimization which can move flip-flops across combinational logic for improved timing at the cost of increased synthesis time.

## 6. Icarus Verilog and Cocotb Simulation Reference

Simulation runs either via Icarus Verilog (iverilog/vvp) for Verilog test benches or cocotb for Python-based test benches. Icarus flow: 1) read all Verilog source files (RTL + test bench), 2) elaborate the design (iverilog -o sim.vvp), 3) run the simulation (vvp sim.vvp). The server captures stdout for pass/fail detection (looking for "PASS" or "FAIL" patterns, $finish/$stop system tasks) and stderr for compilation errors. VCD waveform files are generated when the waves=true parameter is set using $dumpfile and $dumpvars in the test bench. Cocotb tests run via the cocotb test runner which dynamically loads Python test modules and attaches to the Icarus compiled simulation. The server builds the simulation with cocotb's makefile integration. Coverage metrics are extracted from the simulation log where supported. The timeout parameter prevents runaway simulations from blocking the server.

## 7. OpenLane Place-and-Route Engine Reference

OpenLane runs inside a Docker container with the complete open-source place-and-route toolchain. The flow stages are: synthesis (Yosys synthesis to gate-level netlist), floorplan (initial die area allocation and I/O pad placement using init_fp), placement (global placement with RePlAce, detailed placement with OpenDP using the TritonMacroPlacer), clock tree synthesis (CTS with TritonCTS inserting clock buffers to meet skew targets), routing (signal routing with FastRoute global routing and TritonRoute detailed routing using multiple metal layers), signoff (final DRC checking with Magic, LVS with netgen, timing with OpenSTA, antenna rule checking, and metal fill insertion). The server passes configuration via OpenLane's config.tcl file. Key configuration variables: FP_CORE_UTIL (core utilization percentage, typical 30-50 for dense designs), DIE_AREA (die dimensions in microns), IO_MODE (1 for 1-sided, 2 for 2-sided pad rings), PL_TARGET_DENSITY (placement density target), CLOCK_PERIOD (target clock period in nanoseconds), CTS_TARGET_SKEW (clock skew target), ROUTING_STRATEGY (aggressive vs conservative routing), and MACRO_PLACEMENT (fixed macro positions). The server sets sensible defaults for these parameters but advanced users can override any via pr_configure.

## 8. PDK Installation and Configuration

The SkyWater Sky130 PDK is the primary target technology for the server. Installation via volare: volare enable --pdk sky130 {version_hash} (e.g. volare enable --pdk sky130 0a6b2e3). This installs the PDK under PDK_ROOT/sky130A/. Directory structure: libs.ref (reference libraries with cells, lef, lib, gds, spice, tech files), libs.tech (technology files for each EDA tool: magic, netgen, openlane, klayout, ngspice). Key libraries: sky130_fd_sc_hd (High Density standard cells, 300-500 cells including combinational and sequential), sky130_fd_sc_hvl (High Voltage Level shifters), sky130_fd_io (I/O cells), sky130_fd_pr (Primitive devices like resistors and capacitors), sky130_fd_sram (SRAM macros). The GF180MCU PDK (GlobalFoundries 180nm) and IHP SG13G2 (130nm BiCMOS) follow similar structures. PDK_ROOT is checked at startup and reported in chip_status and chip_available_pdks.

## 9. EDA Tool Discovery and PATH Resolution

At startup the server runs EDA tool discovery by probing PATH using the where command (Windows) or which command (Unix). Discovered tools: yosys (synthesis), iverilog (simulation compilation), vvp (simulation execution), openlane (place-and-route), docker (container runtime for OpenLane), magic (DRC and layout viewer), netgen (LVS comparison), sta (Static Timing Analysis), volare (PDK manager). Each tool is independently recorded in the _state tools dictionary. The server starts successfully with no tools installed -- every tool returns success=False with a descriptive error indicating the missing tool and installation guidance. This design enables the server to function as a documentation and planning tool even without the EDA toolchain installed. The discovery results are accessible via chip_status and the REST API at /api/v1/status.

## 10. OpenSTA Static Timing Analysis Reference

OpenSTA analyzes circuit timing by propagating timing signals through the gate-level netlist using the Liberty timing models. The analysis setup requires: the gate-level Verilog netlist (from Yosys synthesis), the Liberty library file (.lib) for the target PDK and operating condition, and an SDC (Synopsys Design Constraints) file with clock definitions and timing exceptions. The server constructs a STA TCL script that reads the netlist, links the design, reads the Liberty library, reads the SDC constraints, and runs report_timing for the worst setup and hold paths. The report is parsed for slack values, delay contributions (cell delay, wire delay for each stage), and the critical path endpoint. The verify_timing tool requires the liberty_file parameter pointing to the appropriate corner (typically the worst-case FF (fast-fast) corner for setup analysis). PDK Liberty files are located under PDK_ROOT/sky130A/libs.ref/sky130_fd_sc_hd/liberty/.

## 11. Chiplab Workflow Engine

Chiplab (Chip Design Laboratory) provides preset-based workflow generation for common ASIC design patterns. Workflow presets define complete flows with parameterized configurations: blinky_sky130 (LED blinker for Sky130, minimal design for first tapeout), counter_sky130 (parameterized counter with configurable bit width), spi_slave_sky130 (SPI slave interface), riscv_sky130 (RISC-V RV32I core, subset flow due to size). Each preset specifies the RTL sources, synthesis target, PDK, OpenLane configuration values, and verification test benches. Workflows are created via the REST API and track execution state across stages. The Chiplab assist endpoint provides natural language guidance for workflow creation and modification using the connected LLM backend.

## 12. Design Rules and Technology Constraints

Each target PDK imposes design rules that the place-and-route flow must satisfy for manufacturability. Sky130 basic rules (simplified): minimum metal width 0.17um (metal1), minimum metal spacing 0.17um, minimum transistor gate length 0.15um (actual 130nm effective), metal stack includes 5 metal layers (metal1-5) plus top metal (metaltop) with via layers via, via2, via3, via4 between them. The DRC verification tools check against the full rule deck (hundreds of rules). Key constraints to keep in mind during design: clock tree synthesis maintains clock skew under 10% of clock period for reliable operation, signal routing uses up to 5 metal layers optimizing for congestion, antenna rules prevent charge damage during manufacturing, and density rules ensure uniform metal distribution for CMP planarization. The PDK also defines the standard cell layout grid: Sky130 uses a 0.46um (contacted poly pitch) routing grid. Designs that respect these constraints during RTL design (avoiding excessive combinational depth for high clock frequencies, managing fanout) require fewer place-and-route iterations. The server provides these constraints as reference through the chip_available_pdks tool and the documentation system.

## 13. Tool Discovery and Capability Matrix

At startup the server probes PATH for each EDA tool and builds a capability matrix. The matrix is accessible via chip_status and determines which tools are operational. The capability matrix includes per-tool version detection and feature probing where available: Yosys version reported via yosys -V includes synthesis features like commonly used commands (read_verilog, proc, opt, fsm, memory, techmap, abc, write_verilog). Docker availability includes running status (docker info must succeed not just docker --version). Iverilog availability includes both iverilog and vvp binaries. The capability matrix is stored in _state tools and is recalculated at each server restart. Tools that are not available return clear error messages with installation instructions including package manager commands where applicable. The server never attempts EDA operations with missing or partial toolchains -- every EDA tool call validates availability before execution.

## 15. Verification Tool Parameter Reference

The verify_drc parameters: design_name (str, optional run DRC on an OpenLane design by name), gds_path (str, optional run DRC on a specific GDS file), pdk (str, default sky130, target PDK for rules). The verify_lvs parameters: design_name (str, required), pdk (str, default sky130). The verify_timing parameters: top_module (str, required), sdc_file (str, optional path to SDC constraints), liberty_file (str, optional path to Liberty library). The verify_formal parameters: golden_model (str, required path to reference Verilog), revised_model (str, required path to implementation Verilog), top_module (str, required). All verification tools return structured results with success boolean and parsed report data accessible through the result dict. The verification tools parse EDA tool stdout using regex patterns specific to each tool's output format. DRC violation counts are extracted from Magic output lines matching "Number of violations = N". LVS results parse netgen's "Netlists match" or "Netlists differ" output. Timing results extract slack values from OpenSTA's report_timing output. Formal results report equivalence or counterexample from Yosys SAT output.

## 16. Asynchronous Design Flow Execution

The server executes EDA operations asynchronously using asyncio.create_subprocess_exec. Each tool call spawns a subprocess and awaits its completion with a configurable timeout. This design prevents blocking the MCP server during long operations (OpenLane runs can take hours). The subprocess communication captures stdout and stderr separately for diagnostic access. The server handles several edge cases: tool not on PATH returns FileNotFoundError, tool hangs exceeds timeout returns structured timeout error, tool returns non-zero exit code includes full stderr in the response, and Docker not running returns connection refused. The async design also enables concurrent operations: synthesis and simulation can run simultaneously for independent blocks. OpenLane operations are serialized at the design level to prevent resource conflicts. The activity log records each subprocess execution with duration, exit code, and error status for performance monitoring and debugging.

## 17. Prefab Card Tool Reference

Six Prefab App tools are registered for rich in-chat visualization: show_chip_status_card displays EDA tool availability as a grid of green/red indicators with PDK status and work directory info. show_pdks_card lists available PDKs with installation status and technology node info. show_pipeline_card displays the 11-stage RTL-to-GDSII pipeline as a visual flowchart. show_depot_card lists files in a depot directory (uploads, outputs, or designs) as a file table. show_cells_stats_card shows standard cell library statistics (cell count by type, drive strengths). show_cells_list_card displays standard cell search results as a card. Prefab tools are toggled via CHIP_DESIGN_MCP_PREFAB_APPS=0 environment variable. They require an MCP client that supports MCP Apps (Claude Desktop, Cursor with limited support).

## 18. REST API Endpoint Reference

The server exposes REST API on port 11022 alongside MCP tools. GET /api/v1/status returns JSON with server name, version, EDA tool availability (per-tool boolean), PDK installed status and root path, work directory paths, and uptime in seconds. GET /api/v1/tools returns sorted list of all registered MCP tool names with count. POST /api/v1/control/{tool_name} dispatches a tool call with JSON body parameters and returns the tool result. GET /api/capabilities returns feature announcements including prefab apps status, sampling capability, skills provider, prompts, resources, help slugs, and endpoint URLs. GET /.well-known/mcp/manifest.json returns the LobeHub manifest. GET /api/v1/tools/detail returns tool catalog with domain prefix and first docstring line for each tool. GET /api/v1/fleet performs bounded port scan (10700-11100) returning discovered server names, versions, and ports. GET /api/v1/llm/status probes Ollama and LM Studio returning provider (ollama/lmstudio), ok status, and available model. POST /api/v1/llm/chat proxies chat messages to the detected local LLM. GET /api/v1/help returns help slugs index with count. GET /api/v1/help/{slug} returns markdown content for the given documentation slug. POST /api/v1/upload accepts file uploads returning filename and size. GET /api/v1/list lists files in uploads, outputs, or designs directories. GET /api/v1/download/{file_name} downloads a file with file streaming. All GET endpoints support JSON and CORS for cross-origin access from the web dashboard on port 11023. The FastAPI framework provides automatic OpenAPI documentation at /docs (Swagger) and /redoc (ReDoc). Error responses follow JSON:API conventions with detail strings in the response body.
